# grounded-rag

[![tests](https://github.com/downmeansoff/grounded-rag/actions/workflows/tests.yml/badge.svg)](https://github.com/downmeansoff/grounded-rag/actions/workflows/tests.yml)
![tests](https://img.shields.io/badge/tests-145%20passed-brightgreen)
![python](https://img.shields.io/badge/python-3.11-blue)
![postgres](https://img.shields.io/badge/store-pgvector-336791)

Grounded RAG движок, собранный с нуля: ingestion, chunking, embedding, векторный поиск в Postgres и ответ с цитатами.

Принцип всего движка: модель отвечает только по найденным документам. Если ответа в них нет, она обязана сказать это прямо, а не заполнить пробел общими знаниями. Непроверяемое утверждение хуже отсутствующего.

Первый тестовый корпус: реальная тендерная документация госзакупок (14 документов, 550 чанков).

## Архитектура

```
domain.profiles        под что подогнан движок: разбор исходного файла и обе формулировки для LLM
chunk.recursive        рекурсивный чанкер 1500/200, режет по абзацам, затем предложениям, затем символам
embed.local            intfloat/multilingual-e5-base локально, без ключа, с query/passage префиксами E5
embed.gigachat         тот же протокол Embedder поверх GigaChat Embeddings, батчами по 32 текста
embed.factory          выбор бэкенда по EMBEDDING_BACKEND, с проверкой размерности до всякой работы
llm                    один клиент GigaChat на процесс плюс узкий протокол ChatModel, чтобы тесты не ходили в сеть
contextual             перед эмбеддингом LLM дописывает чанку его место в документе, ответы кэшируются на диск
store.postgres         psycopg3 + pgvector, HNSW индекс, гибридный поиск: вектор + полнотекст, слияние через RRF
rerank.cross_encoder   BAAI/bge-reranker-base поверх кандидатов, выключен по умолчанию
retrieve               политика поиска целиком: гибрид, затем rerank, если включён
generate.gigachat_llm  ответ с цитатами поверх найденных чанков, честный отказ при отсутствии ответа
```

## Запуск

```bash
docker compose up -d
py -3.11 -m venv .venv
.venv/Scripts/pip install -e ".[dev]"
cp .env.example .env
```

Порт Postgres задаётся через `POSTGRES_PORT` в `.env` и `docker-compose.yml`. По умолчанию 5433, а не 5432: на машине разработки 5432 занят нативным сервисом postgres.

```bash
python scripts/ingest.py "path/to/docs"
python scripts/ingest.py --force "path/to/docs"   # переиндексировать всё заново
python scripts/query.py "уборка помещений клининг"
python scripts/ask.py "какой график работы?"
python scripts/ask.py "какой график работы?" --filter "Заказчик=музей"
```

Повторный `ingest` трогает только изменившиеся документы. Отпечаток считается от содержимого документа и от настроек сборки индекса разом, поэтому смена модели эмбеддингов, размера чанка или профиля переиндексирует корпус целиком, а добавление одной закупки к тысяче стоит одной закупки. Что именно входит в отпечаток, написано в [`index_key.py`](src/grounded_rag/index_key.py).

`ask.py` требует `GIGACHAT_CREDENTIALS` в `.env`: ключ авторизации из личного кабинета developers.sber.ru, раздел API, GigaChat API.

## Демонстрационный корпус

Настоящая выгрузка тендеров в репозиторий не выкладывается: это чужие документы. Чтобы движок можно было прогнать сразу после клонирования, в `sample/docs` лежат шесть вымышленных тендеров, написанных вручную в том же формате, что и выгрузка, а в `eval/sample.json` лежит разметка к ним.

```bash
python scripts/ingest.py sample/docs
python scripts/evaluate.py sample/docs eval/sample.json
```

Ни одной платной операции: эмбеддинги локальные, Contextual Retrieval и rerank по умолчанию выключены. Нужен только поднятый Postgres.

Замер на демо-корпусе, 6 документов и 25 чанков, гибридный поиск:

```
hit@5 13/14 = 0.93   MRR@10 0.853   recall@5 0.93

Вопросы с фильтром по метаданным (в числа выше не входят):
+ demo-badges-filtered    без фильтра: позиция 1   с фильтром: позиция 1   Заказчик=БИБЛИОТЕКА
+ demo-tokens-filtered    без фильтра: позиция 7   с фильтром: позиция 1   Заказчик=ДВОРЕЦ СПОРТА
```

Эти числа не сопоставимы с числами из раздела «Оценка качества поиска»: там настоящий корпус из 14 тендеров, здесь шесть коротких документов, написанных одним человеком, поэтому поиску тут заметно легче. Демо-корпус нужен не для оценки движка, а для того, чтобы весь путь от ingest до замера воспроизводился на чужой машине.

Один документ в наборе, `demo-06`, содержит раздел `[doc(bin)]`. Это воспроизводит поведение на настоящей выгрузке: вложения в устаревшем двоичном формате `.doc` парсер профиля не берёт, и такой раздел в индекс не попадает.

## Гибридный поиск

Retrieval идёт двумя дорогами сразу: векторной по эмбеддингам и полнотекстовой по `tsvector` с русской конфигурацией. Списки сливаются через Reciprocal Rank Fusion.

Складываются не скоры, а обратные ранги: `SUM(1 / (60 + rank))`. Косинусное расстояние и `ts_rank_cd` живут в разных шкалах, и нормализация этих шкал зависит от выборки, то есть плывёт от запроса к запросу. Рангам шкала не нужна вовсе, важно только положение чанка в каждом списке.

Зачем это на реальном корпусе: запрос по номеру закупки `0312100006326000036`.

```
vector: 32616331526, 0356300055026000130, 0152100007026000006   нужного тендера нет вообще
hybrid: 0312100006326000036, 32616331526, 0356300055026000130   нужный тендер первый
```

Эмбеддинги плохо различают длинные цифровые идентификаторы: 19 цифр для модели почти неотличимы от других 19 цифр. Полнотекстовый индекс находит их точно. В `tsvector` попадает не только текст чанка, но и `doc_id` с `part_name`: идентификатор документа внутри текста обычно не встречается, он живёт в метаданных.

Название документа туда не попадает, и это проверено, а не забыто. Выглядит логично: закупка называется «Услуги вахтера (сторожа)», внутри её текста слово «вахтер» может не встретиться ни разу, и вопрос про вахтёра такую закупку не найдёт. Собрал, померил на двух наборах сразу: ни одна метрика не сдвинулась ни на сотую, ни на настоящем корпусе (0.74 против 0.74), ни на демонстрационном (0.93 против 0.93). Замер честный: тот же индекс и те же векторы, отличается только заполнение колонки с названием, потому что `tsvector` пересчитывается сам. Причина неподвижности та же, по которой в автофильтре есть второй отсев: тринадцать из четырнадцати закупок называются «Оказание услуг по гардеробному обслуживанию» с точностью до порядка слов, и слово из такого названия не различает документы, а просто есть у всех. Правка откачена, дублирование названия в каждый чанк за ноль выигрыша того не стоит.

## Фильтр по метаданным

Поиск умеет сужаться до части корпуса: `--filter "Заказчик=музей"`, ключ и значение из метаданных документа. Значение ищется подстрокой без учёта регистра, потому что метаданные это человеческие строки, и требовать полного юридического имени заказчика значит не дать фильтром пользоваться. Ключ `doc_id` зарезервирован и сравнивается целиком: идентификатор закупки это адрес, а совпадение по началу номера означало бы ответ по чужому тендеру. Несколько условий складываются через И.

Важна не сама возможность, а место фильтра в запросе: он стоит внутри обоих поисков, до отбора кандидатов, а не поверх слияния RRF.

```sql
FROM chunks c
JOIN documents d ON d.doc_id = c.doc_id AND d.meta ->> %(fk0)s ILIKE %(fv0)s
ORDER BY c.embedding <=> %(vec)s::vector
LIMIT %(candidates)s
```

Отсекай движок лишнее после слияния, кандидатов набралось бы тридцать по всему корпусу, фильтр вычеркнул бы из них почти всё, и нужный чанк, стоявший в общем списке сороковым, не попал бы в выдачу вовсе. А это ровно тот случай, ради которого фильтр и нужен: узкий вопрос по документу, который в общем рейтинге стоит низко.

Ключей метаданных движок не знает заранее, они приходят от профиля. Поэтому неизвестный ключ даёт пустую выдачу, а не тихий поиск по всему корпусу: опечатка в имени ключа не должна читаться как «в документах такого нет». По той же причине пустая выдача под фильтром говорит про фильтр, а не про корпус.

## Заказчик из текста запроса

Фильтр работает, но задавать его приходится руками, хотя в самом вопросе имя заказчика обычно уже есть: «какой штраф в тюменской поликлинике». Флаг `--auto-filter` достаёт его оттуда и кладёт в тот же фильтр по метаданным.

```bash
python scripts/query.py "какой штраф в тюменской поликлинике" --auto-filter
python scripts/ask.py "сколько мест в гардеробе новосибирского университета" --auto-filter
```

Подстрокой это не ловится ни в одну сторону: в вопросе «тюменской поликлинике», в метаданных «ТЮМЕНСКОЙ ОБЛАСТИ ... ГОРОДСКАЯ ПОЛИКЛИНИКА №5». Поэтому обе стороны прогоняются через `to_tsvector('russian')`, тот же словарь Postgres, что и полнотекстовая половина поиска: две разные нормализации в одном движке рано или поздно разъезжаются.

Лексема голосует за заказчика, только если проходит два отсева, и второй появился из замера, а не из рассуждения.

Первый отсев: лексема встречается ровно у одного заказчика. «Государственное», «бюджетное», «учреждение» есть почти у всех, и со счётом по ним побеждал бы тот, у кого длиннее название.

Одного этого мало. Первая версия правила уронила замер: `hit@5` с 0.74 до 0.72. Виноват один вопрос, «нужны ли гардеробщикам медицинские книжки»: лексема «медицинск» стоит в названии ровно одного заказчика, поиск сузился до медицинского университета, а ответ там не лежит. Отсюда второй отсев: лексема должна быть редкой в тексте самого корпуса. Данные разделяют имена и слова предметной области с большим запасом:

```
медицинск   9 документов из 14      связ   11 из 14      порог: 0.25 корпуса
тюменск     1 из 14                 уральск  1 из 14     мордовск 1 из 14
архитектурн 0 из 14                 шолом-алейхем 1 из 14
```

Побеждает заказчик с наибольшим числом совпавших лексем. Ноль совпадений или ничья означают, что фильтра нет: искать по всему корпусу хуже, чем найти сразу, но лучше, чем сузить корпус до чужого заказчика и получить уверенный ответ не из того документа. Заданный руками `--filter` по тому же ключу сильнее угаданного, иначе опечатка в имени заказчика молча подменялась бы догадкой движка.

Что это дало на наборе из 46 вопросов: фильтр срабатывает на 10, все 10 угаданы верно, ложных срабатываний ноль. `hit@5` не меняется (0.74), `MRR@10` растёт с 0.617 до 0.630. Двигаются ровно два вопроса: «какой штраф в тюменской поликлинике» с «не найдено в топ-10» на восьмое место, «какой код ОКПД2 у закупки в консультативно-диагностическом центре» со второго на первое.

Числа скромные, и это честная картина ступени, а не разочарование: на большинстве вопросов заказчик не назван вовсе, и там правильное поведение это молчать. Работает она на том меньшинстве, где имя названо, и цена ошибки там высокая. Поэтому автофильтр сидит за явным флагом, а не внутри `retrieve`: подстановка условия, которого пользователь не писал, должна быть видимой, и каждый скрипт печатает, что именно он подставил.

Ключ метаданных с именем владельца документа приходит от профиля (`filter_key`). У `plain` и `markdown` его нет: у произвольного текста владельца из метаданных не достать, и там автофильтр молча ничего не подставляет.

## Rerank

Модель поиска кодирует запрос и чанк по отдельности, поэтому близость считается между двумя сжатыми до вектора смыслами. Этого хватает, чтобы вытащить тридцать правдоподобных кандидатов, но не хватает, чтобы отличить первого из них от пятого.

Cross-encoder читает пару «запрос плюс чанк» вместе и выдаёт одно число: отвечает ли этот чанк именно на этот запрос. Он дороже на документ на порядки, поэтому применяется не к корпусу, а к короткому списку кандидатов от гибридного поиска.

Запрос «какой график работы гардероба», топ-5 до и после:

```
гибрид:  Контракт#40 | Описание#0 | Гардероб#0 | Гардероб#10 | Контракт#2
rerank:  Гардероб#10 | Описание#17 | Описание#5 | Описание#5 | Описание#4
```

Чанк `Гардероб#10` содержит буквально таблицу режима работы («Понедельник-Пятница с 07:30-19:00, суббота по графику, воскресенье выходной»). Гибридный поиск поставил его четвёртым, cross-encoder поднял на первое место с отрывом: 0.83 против 0.22 у третьего.

Выключен по умолчанию: вторая модель весом около гигабайта живёт в памяти рядом с эмбеддером. Включается `USE_RERANK=true` в `.env`.

## Contextual Retrieval

Чанкер режет документ по абзацам, и середина документа приезжает в индекс без единого признака того, откуда она. Фрагмент «Штраф начисляется за каждый факт неисполнения» не содержит ни слова «гардероб», ни имени заказчика, ни названия раздела. Искать его при этом будут именно по ним.

Поэтому перед индексацией LLM пишет одно-два предложения о том, к чему относится фрагмент. Склейка «контекст плюс текст» уходит в эмбеддер, `context` попадает в `tsvector` рядом с текстом (в оригинальной статье Anthropic это называется contextual BM25), а в цитату пользователю уходит оригинальный текст. Контекст меняет то, как чанк находится, но не то, что показывается: пользователь должен видеть документ, а не пересказ документа моделью.

Замер на всём корпусе (550 чанков, 14 тендеров), запрос «какой штраф за неисполнение обязательств по гардеробу», топ-5. Звёздочка это чанк тендера `0312100006326000036`, в контракте которого штрафы и прописаны:

```
без контекста:  чужой расчёт НМЦК | *Контракт#23 | *Контракт#21 | чужое описание | *Контракт#27   3 из 5
с контекстом:   *Контракт#21 | *Контракт#22 | *Контракт#27 | *Контракт#23 | *Контракт#25          5 из 5
```

Первое место без контекста занимала таблица расчёта начальной цены чужой закупки: в ней тоже есть слова «гардероб» и «услуги», а про штрафы там нет ничего. С контекстом всю пятёрку занимают чанки того контракта, где условие о штрафах и лежит.

Обе стороны считаны одним прогоном на одном корпусе и одном эмбеддере, скриптом `scripts/measure_contextual.py --all`: он снимает контекст со всего корпуса, спрашивает, возвращает контекст и спрашивает то же самое. Вторая индексация за LLM не платит, контексты приходят из кэша.

Насколько этому числу можно верить. Запросов было четыре, и заметно выиграл один. На «сколько стоит гардеробное обслуживание» и «кто заказчик услуг гардероба» выдача сдвинулась, но сказать, стала она лучше или хуже, нечем: у этих запросов нет одного правильного тендера, гардероб закупают все четырнадцать. На «требования к персоналу гардеробщика» звёздочек стало меньше, зато в топ поднялось «Извещение гардеробщики», где требования к персоналу и написаны. То есть метрика «сколько чанков выбранного тендера в топ-5» честно работает только там, где ответ заведомо лежит в одном документе, и обобщать её на весь корпус нельзя.

И первая версия промпта прироста не дала совсем: она перечисляла варианты ответа («раздел, предмет закупки, сторона договора, этап») и получала в ответ выбранный вариант одним словом, «Этап». Слов, которых в чанке ещё нет, такой контекст не приносит. Помогло требование законченного предложения с явно названными предметом закупки и заказчиком плюс пример ответа. На 550 контекстах второй версии вырожденных (короче 40 символов) не осталось ни одного, средняя длина 169 символов.

Отличие от варианта Anthropic вынужденное. В оригинале в промпт кладут документ целиком и экономят на prompt caching. У GigaChat кэша промптов нет, а бесплатный тариф конечен, поэтому в промпт уходит шапка документа (первые `CONTEXTUAL_HEAD_CHARS` символов, где обычно и стоит описание объекта закупки) плюс метаданные тендера.

Выключено по умолчанию, `USE_CONTEXTUAL=true` в `.env`: это единственная часть индексации, которая тратит платный ресурс. Вызов приходится на каждый чанк: весь корпус это 550 вызовов и около десяти минут строго последовательно (бесплатный тариф даёт один поток). Ответы кэшируются на диск атомарной записью после каждого чанка, ключ считается от текста чанка и версии промпта, так что повторный ingest бесплатный, обрыв на лимите не теряет уже оплаченное, а правка промпта честно обесценивает старые контексты. Упавший вызов не роняет прогон: чанк идёт в индекс без контекста, а счётчик в конце говорит, сколько таких.

Два вида отказа при этом разделены, потому что снаружи они выглядят одинаково, а лечатся по-разному. `429` и сетевой обрыв временные, они повторяются с растущей паузой (2, 4, 8 секунд): сервер просит не частить, и повтор через сто миллисекунд просит ровно того же ещё раз. `402 Payment Required` означает исчерпанный тариф, и повтор его не лечит. Такой отказ поднимает `QuotaExhausted`, прогон перестаёт дёргать модель совсем и досчитывает оставшиеся чанки как пропущенные: пятьсот обречённых запросов подряд стоят минут и не приносят ни одного контекста. Кэш при этом продолжает работать, так что прогон после пополнения продолжает с места обрыва.

## Оценка качества поиска

Метрика «сколько чанков нужного тендера попало в топ-5» работает только там, где ответ заведомо лежит в одном документе, и на запросе «кто заказчик услуг гардероба» не значит ничего: гардероб закупают все четырнадцать. Поэтому разметка привязана не к документу, а к дословному фрагменту текста. Чанк релевантен, если содержит фрагмент, который на вопрос и отвечает.

Такую разметку можно проверить, и она проверяется до всякого замера, двумя проходами. Первый по документам: фрагмент обязан лежать в том тендере, за которым записан, и не встречаться в чужих. Второй по индексу: фрагмент обязан целиком помещаться в один чанк, потому что фраза может стоять на границе абзацев и развалиться при чанкинге, и тогда её не найдёт никакой поиск. Не сошлось хоть в одном месте, и прогон падает с текстом претензии, а не показывает ноль: ноль от плохого поиска и ноль от кривой разметки выглядят одинаково, а значат разное. На первом же запуске проверка поймала три ошибки в моей собственной разметке, все три вида «этот же ответ есть ещё и вот тут».

Вторая проверка заодно очерчивает границу набора: в индекс попадает не весь тендер целиком. Часть приложений выгрузка помечает `[doc(bin)]`, то есть старым бинарным `.doc`, из которого текст вынуть не удалось, и такие разделы профиль не берёт. У тендера `0372200066226000148` из-за этого всего шесть чанков против пятидесяти с лишним у соседей. Эталоны берутся только из проиндексированного текста, иначе набор мерил бы не поиск, а полноту разбора вложений.

Набор: 50 вопросов, 69 эталонных фрагментов, `eval/labeled.json`. В общие числа идут 46 вопросов без фильтра (65 фрагментов), ещё четыре помечены фильтром по метаданным и считаются отдельным блоком. Вопросы идут через ту же функцию `retrieve`, что и `ask.py`, так что мерится рабочий поиск, а не отдельная его копия для красивых чисел.

```bash
python scripts/evaluate.py "path/to/docs"                # гибрид
python scripts/evaluate.py --vector "path/to/docs"       # только эмбеддинги
python scripts/evaluate.py --rerank "path/to/docs"       # гибрид плюс cross-encoder
python scripts/evaluate.py --auto-filter "path/to/docs"  # гибрид плюс заказчик из текста вопроса
```

Режимы отличаются ровно одной ступенью каждый, индекс при этом один и тот же (модель эмбеддингов `multilingual-e5-base`, 768):

```
только вектор         hit@5 0.72 (33/46)   MRR@10 0.595   recall@5 0.65
гибрид                hit@5 0.74 (34/46)   MRR@10 0.617   recall@5 0.68
гибрид + автофильтр   hit@5 0.74 (34/46)   MRR@10 0.630   recall@5 0.68
гибрид + rerank       hit@5 0.70 (32/46)   MRR@10 0.457   recall@5 0.66
```

`hit@5` это «нашлось ли вообще», ровно то, что чувствует пользователь. `MRR@10` различает первое место и пятое, а глубина 10 больше k, чтобы «нашлось седьмым» отличалось от «не нашлось». `recall@5` считается по эталонам, а не по позициям: если на вопрос отвечают четыре документа, а поиск принёс два, это 0.5, даже когда все пять мест заняты.

Что из этих чисел видно. Полнотекст трогает всего два вопроса из сорока шести, зато один из них переворачивает целиком: «требуется ли банковское сопровождение контракта» у вектора не находится в топ-10 вовсе, у гибрида стоит первым. В документе это дословная строка «Банковское сопровождение контракта не требуется», и вектор растворяет её в общей тендерной лексике, а полнотекст находит по редкому слову. Второй сдвиг косметический, с седьмого места на восьмое.

Rerank же тянет метрики в разные стороны, и это его честная картина, а не шум измерения. Он переставляет 31 вопрос из 46, то есть две трети выдачи, и по сумме теряет два: находит четыре, которых гибрид не нашёл («сколько гардеробщиков должно работать в смене минимум», «что указано на жетоне», «какие вещи гардероб не принимает на хранение» с «не найдено» на первое, третье и второе места, «когда исполнитель не отвечает за пропажу вещей» с восьмого на первое), и теряет шесть, которые гибрид находил («размер обеспечения заявки» и «до скольки работает гардероб в новосибирском» с первого места, «с какого и по какое число оказываются услуги» и «сколько процентов составляет обеспечение исполнения» со второго уходят за топ-10, ещё два уезжают на седьмое место). MRR он роняет сильнее всего, с 0.617 до 0.457, потому что сдвигает вниз ровно те ответы, которые вектор уже поставил первыми: «какой график дежурства у вахтера» и «какой день недели выходной» с первого на четвёртое, «по каким адресам в Кызыле» с первого на третье.

Польза от него тоже видна, но узкая: на вопросах с несколькими правильными фрагментами он дособирает их в пятёрку, «кто делает влажную уборку» с 0.40 до 0.80, «какую спецодежду выдают» с 0.50 до 0.75. Общий recall это не спасает (0.66 против 0.68), потому что теряет он там же, где выигрывает. Вывод практический: на этом корпусе cross-encoder не окупается, и включать его стоит только под конкретный класс вопросов, где ответ собирается из нескольких документов.

Сорок шесть вопросов это всё ещё немного: один вопрос здесь стоит 0.02 по hit@5, и различать изменения меньше этого шага набор не даёт. Числа выше стоит читать как «полнотекст помогает, cross-encoder меняет профиль ошибок и по сумме проигрывает», а не как рейтинг с точностью до третьего знака.

Восемь вопросов на этой модели не находятся ни в одном режиме, и пять из них одной природы. «Общее количество часов работы гардеробов по контракту», «какой ранее исполненный договор требуется от участника закупки», «нужна ли справка об отсутствии судимости у работников», «может ли заказчик потребовать замены работника исполнителя», «отвечает ли исполнитель за привлеченных субподрядчиков» целиком собраны из слов, которые есть в каждом из 550 чанков: контракт, часы работы, участник закупки, договор, замена работника, ответственность. Ответ при этом лежит в одном документе из четырнадцати, а отличающий его токен в запросе не назван (в первом случае это число 2499, во втором предмет договора), и отделить нужный чанк от пятисот таких же не могут ни полнотекст, ни cross-encoder.

Ещё два проигрывают не корпусу, а соседям по своему же документу. «Кто оплачивает восстановление утерянных номерков»: лексема «номерк» стоит в шести тендерах из четырнадцати, и нужный чанк соревнуется с десятками таких же про выдачу и приём номерков. «В каком режиме оказываются услуги вахтера в Омске»: город выделяет документ однозначно, но контекст, приписанный к чанку при индексации, ставит «Омской области» и в тот чанк, где ответ, и во все соседние, так что внутри документа это слово не различает ничего, а «круглосуточно» встречается там ещё и в правиле про видеонаблюдение.

Восьмой, «какой штраф грозит исполнителю за нарушение договора в тюменской поликлинике», ломается иначе, и ломает его как раз попытка сузить вопрос словами. Слово «тюменской» в документе есть, но в чанках с реквизитами и адресами, а ни в одном чанке со штрафом его нет: и вектор, и полнотекст уводит к реквизитам.

Часть из них чинит фильтр по метаданным, и в наборе он теперь проверяется. Четыре вопроса помечены полем `filters`, и рядом с каждым печатается его же выдача без фильтра:

```
+ two-wardrobes-hours-filtered   без фильтра: не найдено в топ-10   с фильтром: позиция 1   Заказчик=ЛЕЧЕБНО-РЕАБИЛИТАЦИОННЫЙ ЦЕНТР
+ min-staff-per-shift-filtered   без фильтра: не найдено в топ-10   с фильтром: позиция 2   Заказчик=ЛЕЧЕБНО-РЕАБИЛИТАЦИОННЫЙ ЦЕНТР
+ cleaning-experience-filtered   без фильтра: не найдено в топ-10   с фильтром: позиция 2   Заказчик=НАДЗОРУ В СФЕРЕ ЗДРАВООХРАНЕНИЯ
+ tyumen-fine-filtered           без фильтра: позиция 4             с фильтром: позиция 1   Заказчик=ГОРОДСКАЯ ПОЛИКЛИНИКА №5

с фильтром: hit@5 4/4 = 1.00   MRR@10 0.750   recall@5 1.00
```

Считаются они отдельно и в общие 0.74 не входят: фильтр сужает корпус до одного заказчика, попасть по такому вопросу заметно легче, и подмешать эти четыре строки в ту же среднюю значило бы поднять её работой, которую поиск не делал. Смысл строки в разнице между двумя её половинами, а не в самой по себе позиции.

Последняя строка поучительна отдельно. Это тот самый вопрос про штраф, и разница с общим набором ровно одна: слова про тюменскую поликлинику убраны из текста запроса и заказчик перенесён в фильтр. В запросе название заказчика поиску мешало, в метаданных то же название поставило ответ первым.

Первые же два провала объясняются не только фильтром: замер на второй модели ниже показывает, что `multilingual-e5-small` находит их и без него, четвёртым и пятым. То есть упирались они не в устройство поиска, а в то, как конкретная модель разложила однообразные формулировки.

## Что будет на тысяче документов

Четырнадцать тендеров это корпус для отладки, а не рабочий размер. Архив закупок за год это сотни документов, и все они одной предметной области, то есть написаны теми же словами, что и нужный. Вопрос, на который надо ответить числом: во что превращается выдача, когда у правильного чанка становится в семьдесят раз больше похожих соседей.

Замер устроен так. Вопросы и эталоны те же самые, ответы всё время лежат в тех же четырнадцати тендерах, а вокруг них добавляются чужие закупки. Меняется ровно одно, размер корпуса.

Шум сделан намеренно тяжёлым: он собран из кусков этих же четырнадцати документов, перемешанных между собой, поэтому отличить его от нужного текста по лексике нельзя в принципе. Куски с эталонными фразами выброшены, иначе ответ оказался бы сразу в нескольких документах и разметка перестала бы быть верной. Настоящие чужие закупки вытесняли бы слабее: у них другие адреса, суммы и заказчики. Так что числа ниже это верхняя оценка потерь, а не средняя.

Собирает такой шум `scripts/make_noise.py`, и повторить замер можно на демонстрационном корпусе, без настоящей выгрузки:

```bash
python scripts/make_noise.py sample/docs eval/sample.json .noise 200
python scripts/ingest.py .noise
python scripts/evaluate.py sample/docs eval/sample.json
```

```
   14 документов,    550 чанков   hit@5 0.70   MRR@10 0.538   recall@5 0.62
  114 документов                  hit@5 0.41   MRR@10 0.298   recall@5 0.35
  214 документов                  hit@5 0.33   MRR@10 0.271   recall@5 0.28
  514 документов                  hit@5 0.26   MRR@10 0.168   recall@5 0.22
 1014 документов, 59 864 чанка    hit@5 0.13   MRR@10 0.090   recall@5 0.09
```

Поиск по всему архиву разом не работает. Это главный вывод замера, и он не про недостаточную оптимизацию: на тысяче документов из сорока шести вопросов находится шесть.

Инфраструктура при этом не при чём и запас у неё большой. Индекс на 59 864 чанка занимает 577 МБ, гибридный поиск по нему отвечает за 47 мс, с фильтром за 77 мс. Векторную часть держит HNSW, полнотекстовую GIN, и обе рассчитаны на порядки больше.

Чинится это не моделью и не переранжированием, а сужением корпуса до поиска. На том же индексе из 1014 документов четыре вопроса с фильтром по заказчику дают `hit@5 4/4 = 1.00` при `MRR@10 0.708` и полном recall, причём без фильтра ни один из них не находится даже в топ-10:

```
+ two-wardrobes-hours-filtered   без фильтра: не найдено в топ-10   с фильтром: позиция 2
+ min-staff-per-shift-filtered   без фильтра: не найдено в топ-10   с фильтром: позиция 1
+ cleaning-experience-filtered   без фильтра: не найдено в топ-10   с фильтром: позиция 3
+ tyumen-fine-filtered           без фильтра: не найдено в топ-10   с фильтром: позиция 1
```

Отсюда же переоценка автофильтра. На четырнадцати документах подстановка заказчика из текста вопроса не двигала `hit@5` вообще и выглядела украшением. На тысяче она удваивает результат, 0.13 против 0.26, потому что теперь это единственный работающий способ отсечь чужие закупки. На большом корпусе фильтр перестаёт быть опцией и становится основным механизмом, а поиск по всему корпусу превращается в запасной путь для вопросов, где сузить не по чему.

Сама подстановка от роста корпуса не сломалась, и это стоило проверить отдельно: заказчиков стало не четырнадцать, а больше тысячи, и правило «лексема принадлежит ровно одному заказчику» могло начать ошибаться. Замер печатает три исхода отдельно, потому что стоят они разного: молчание возвращает вопрос к поиску по всему корпусу, а промах уводит его в чужую закупку, где ответа нет и быть не может.

```
   14 документов   опознал верно 10, мимо 0, промолчал 36 из 46
 1014 документов   опознал верно  8, мимо 0, промолчал 38 из 46
```

Ни одного промаха на корпусе, выросшем в семьдесят раз. Зато видно, где настоящий предел: восемь вопросов из сорока шести. Дело не в точности правила, а в охвате, потому что в остальных тридцати восьми имя заказчика попросту не названо, и сузить корпус по ним нечем. Улучшать тут надо не правило.

Предел сужения меряется так же просто. Если подставить в фильтр `doc_id` той закупки, где лежит ответ, то есть искать внутри одной известной закупки, на том же корпусе из 1014 документов получается:

```
без фильтра        hit@5 0.13 (6/46)    MRR@10 0.110   recall@5 0.11
фильтр по doc_id   hit@5 0.89 (41/46)   MRR@10 0.729   recall@5 0.79
```

0.89 это больше, чем 0.74 на корпусе из четырнадцати документов вообще без фильтра. Сужение до одного документа не просто отменяет вред от размера архива, оно снимает и часть исходной задачи: конкурентов у правильного чанка остаётся полсотни вместо шестидесяти тысяч.

Практический вывод для архива закупок такой. Свободный поиск по всему архиву бесполезен и обещать его нельзя. Автофильтр по заказчику вытягивает те вопросы, где имя названо, и делает это без единой ошибки. А основной сценарий это поиск внутри закупки, которую пользователь уже открыл: там идентификатор известен заранее, подставлять его ниоткуда не надо, и работает он лучше всего.

Индексация тысячи документов заняла 52 минуты на RTX 3060 и заняла бы около двенадцати часов на процессоре: `torch` по умолчанию ставится колесом под CPU, и это стоит проверить перед первым прогоном. Повторные прогоны считаются от изменившихся документов, а не от всего архива.

## Под что подогнан движок

Тендерная документация это первый корпус, а не единственный. Что именно индексируется, знают ровно три места: чем разбирается исходный файл, что говорится модели, когда она пишет контекст чанка, и что говорится ей, когда она отвечает пользователю. Всё остальное про домен не знает вовсе: чанкер режет текст, эмбеддер считает векторы, гибридный поиск сливает ранги, метрики считают попадания.

Эти три места собраны в `DomainProfile`, и профиль выбирается одной строкой в `.env`:

```bash
DOMAIN=tenders    # выгрузка tenderhunt: шапка с номером закупки, разделы вида "### Название [docx]"
DOMAIN=plain      # любая папка с .txt и .md, файл целиком одним документом
DOMAIN=markdown   # база знаний: YAML frontmatter в метаданные, разделы "##" в части документа
```

Отсюда же вытекает форма хранения. Документ это `doc_id`, заголовок, части и свободный словарь метаданных в JSONB, а не колонки под тендер: у закупки это заказчик и НМЦК, у статьи будут автор и журнал. Метаданные намеренно оставлены вне генерируемой колонки `tsv`, чтобы смена профиля не требовала перестраивать полнотекстовый индекс. Цитата тоже приходит от профиля, поэтому `ask.py` пишет «тендер 0312100006326000036» на одном корпусе и «документ regulation» на другом, без единого `if` в коде ответа.

Профилей три, и это не про удобство: абстракция с одной реализацией ничего не доказывает. `PlainProfile` работает на любой папке с текстом и проверяет, что домен действительно вынут, а не описан на словах. `MarkdownProfile` проверяет то, чего плоский текст проверить не может, потому что документ у него имеет структуру: разделы `##` становятся частями документа и попадают в цитату по имени, а `###` остаётся внутри своего раздела. Оттуда же два случая, которых у первых двух профилей не было. Имя части это адрес чанка, по нему собирается ссылка и по нему контекстуализатор ищет шапку раздела, поэтому два раздела «Установка» в одном файле нумеруются: иначе половина ссылок врала бы молча. А метаданные приходят из frontmatter, то есть их ключи движку заранее неизвестны, и в JSONB они ложатся как есть.

Смена профиля означает пересбор индекса: разбор документов другой, идентификаторы другие, ключ кэша контекстов другой. Порядок такой: удалить таблицы `chunks` и `documents`, поменять `DOMAIN`, запустить ingest заново. Ключ кэша контекстов включает версию промпта профиля, поэтому чужие описания к новым документам не приклеиваются молча.

## Сменный бэкенд эмбеддингов

Векторы считает либо локальная модель, либо GigaChat, и выбирает между ними одна строка в `.env`. Обе реализации закрывают один протокол `Embedder`, а остальной конвейер о выборе не знает: ingest, поиск, ответ и замер спрашивают эмбеддер у `embed/factory.py`.

```bash
EMBEDDING_BACKEND=local      # sentence-transformers, офлайн и бесплатно, по умолчанию
EMBEDDING_BACKEND=gigachat   # сеть и платный тариф, требует EMBEDDING_DIM=1024
```

Смысл второго бэкенда в том, чтобы разницу между моделями можно было померить набором из `eval/`, а не заявить. На GigaEmbeddings замер сделать не удалось: пакет токенов исчерпан, и API отвечает `402 Payment Required`. Код бэкенда готов и покрыт тестами без сети, но числа снять не на чем, поэтому вместо них ниже сравнение двух локальных моделей одного семейства. Прогон повторяемый и бесплатный, ключ для него не нужен.

Обе модели индексировали тот же корпус (14 документов, 550 чанков), с теми же контекстами и тем же полнотекстовым индексом. Отличается только эмбеддер:

```
                      multilingual-e5-base (768)      multilingual-e5-small (384)
только вектор         hit@5 0.72  MRR 0.595  rec 0.65  hit@5 0.74  MRR 0.581  rec 0.68
гибрид                hit@5 0.74  MRR 0.617  rec 0.68  hit@5 0.76  MRR 0.610  rec 0.70
гибрид + автофильтр   hit@5 0.74  MRR 0.630  rec 0.68  hit@5 0.80  MRR 0.631  rec 0.74
гибрид + rerank       hit@5 0.70  MRR 0.457  rec 0.66  hit@5 0.70  MRR 0.511  rec 0.66
```

На гибриде модели сходятся почти в ноль: 34 найденных вопроса из 46 у base, 35 у small, MRR 0.617 против 0.610, recall 0.68 против 0.70. Разница в один вопрос это ровно шаг набора, то есть ничего. Модель вдвое меньше не проигрывает большей ничего заметного, и это первый вывод таблицы.

Второй интереснее: промахиваются они в разных местах. Base не находит двенадцать вопросов, small одиннадцать, общих из них пять. Base не берёт «общее количество часов работы гардеробов», «какой ранее исполненный договор требуется», «нужна ли справка об отсутствии судимости» и ещё четыре, а small ставит их с первого по пятое место. Small не берёт «нужны ли гардеробщикам медицинские книжки», «размер обеспечения заявки», «можно ли курить на рабочем месте», «какой код ОКПД2», «сколько человеко-часов» и «могут ли посторонние находиться в гардеробе», а base ставит их в первую тройку. Почти одинаковая средняя набрана разными вопросами, и никакая одна цифра этого не показывает.

Третий вывод про строку с автофильтром, и он единственный в таблице выходит за шаг набора. У base подстановка заказчика hit@5 не двигает вовсе, у small добавляет два вопроса, 0.76 против 0.80, и поднимает recall с 0.70 до 0.74. Оба вопроса такие, где ответ small и так находил, но клал за пятёркой: «какой код ОКПД2 у закупки в консультативно-диагностическом центре» с девятого места на первое, «сколько человеко-часов в закупке уральского медицинского университета» с шестого на четвёртое. То есть выигрыш здесь не про модель: слабее ранжирующая модель просто оставляет фильтру больше работы.

Четвёртый вывод про сам замер. На прежнем наборе из двенадцати вопросов эта же таблица показывала уверенную победу small, на наборе из двадцати девяти преимущество исчезало полностью, на нынешних сорока шести small снова впереди на вопрос. Ровно это и значит «шаг набора 0.02»: пока разница между моделями меньше двух-трёх вопросов, замер её не различает, и менять из-за неё бэкенд нечестно. Бэкендом по умолчанию оставлена `e5-base`, на которой сняты все числа выше.

Заодно эта же таблица показывает, что rerank вредит обеим одинаково по hit@5 (0.70 у обеих, минус два вопроса у base и минус три у small) и по-разному по MRR: у base он роняет её с 0.617 до 0.457, у small с 0.610 до 0.511. Причина в обоих случаях одна: cross-encoder сдвигает вниз ровно те ответы, которые вектор уже поставил первыми, и меняет их на дособранные документы в вопросах с несколькими правильными ответами.

Смена бэкенда стоит дороже, чем правка одной строки, и вот почему. Модели дают векторы разной длины, 768 и 1024, а колонка `embedding` в Postgres объявляется под конкретное число при создании таблицы и на лету не меняется. `CREATE TABLE IF NOT EXISTS` готовую таблицу оставляет как есть, поэтому без проверки прогон дошёл бы до вставки первого чанка и упал там ошибкой про длину вектора, из которой не видно ни причины, ни что делать. Несовпадение ловится до всякой работы и в двух местах: `make_embedder` сверяет `EMBEDDING_DIM` с выбранным бэкендом, `ensure_schema` сверяет его же с размерностью уже собранной таблицы. Обе ошибки говорят одно: поставить нужный `EMBEDDING_DIM`, удалить таблицу `chunks`, запустить ingest заново.

Ещё два отличия видно прямо в коде. Префиксы `query:` и `passage:` есть только у локального бэкенда: это соглашение семейства e5, на котором его обучали, а модели GigaChat такой префикс ничего не сообщает. И запросы к GigaChat уходят батчами по 32 текста, потому что весь корпус одним запросом это около мегабайта, а любой отказ на таком запросе теряет прогон целиком, а не последний батч.

## Тесты

```bash
.venv/Scripts/python -m pytest tests/ -q
```

Покрыты инварианты чанкера (ни один чанк не длиннее size, overlap повторяет хвост предыдущего, индексы последовательны) и путь честного отказа, который проверяется без обращения к модели.

Фильтр по метаданным проверяется там же, в базе, и главный его тест не про SQL, а про порядок: тридцать чанков чужого заказчика ближе по вектору и только они содержат слово запроса, нужный документ без фильтра не находится вовсе, с фильтром выходит первым. Рядом закреплено, что `_` и `%` внутри значения ищутся буквально, что `doc_id` сравнивается целиком и что неизвестный ключ даёт пусто, а не весь корпус.

Тесты гибридного поиска идут в настоящий Postgres: проверяемое поведение живёт в SQL, и мок вокруг него проверял бы только сам мок. Изоляция от рабочего корпуса сделана отдельной схемой в незакоммиченной транзакции, откат в конце теста сносит её целиком. Без базы эти тесты помечаются skipped, остальные проходят.

Тот же прогон идёт в GitHub Actions на каждый push и pull request, с базой из того же образа `pgvector/pgvector:pg17`, что в `docker-compose.yml`. Перед тестами там же проходит `ruff check .`: правила `E`, `F`, `I`, `UP`, `B`, из которых важнее прочих `B905`, запрет на `zip` без `strict`. В этом коде `zip` соединяет чанки с их эмбеддингами и контекстами, и молчаливое обрезание по короткой последовательности означало бы чанки с чужими векторами, то есть ошибку, которую не увидишь ни в одном падении. Ключи там не нужны: тесты в сеть не ходят, модель эмбеддингов не грузят, а `torch` ставится колесом под CPU, потому что версия с CUDA весит около двух гигабайт и на раннере не нужна ни для чего. Пропуск тестов Postgres в CI запрещён переменной `RAG_REQUIRE_POSTGRES`: локально недоступная база это удобство, а в CI это зелёный прогон, не проверивший ни одного SQL.

Тесты rerank модель не грузят: проверяется не качество её оценок, а то, что оценки применяются правильно (порядок, срез по top_k, сохранность настоящего косинусного расстояния). Скорер подставляется в конструктор.

Тесты Contextual Retrieval в сеть не ходят тоже: LLM за узким протоколом `ChatModel`, в тестах вместо неё заглушка, которая считает вызовы и умеет падать. Проверяется, что в промпт кладётся нужное, что за один и тот же чанк не платят дважды, что кэш переживает перезапуск и битый файл, и что упавший вызов не роняет ingest. Со стороны базы отдельный тест на то, что слово из сгенерированного контекста находит чанк, но в цитату не попадает.

Метрики оценки покрыты без базы и без модели, и проверяется там не качество поиска, а честность линейки: что `hit@5` смотрит ровно в пятёрку, что `recall` считает эталоны, а не занятые места, что различие в пробелах совпадение не ломает, а различие в регистре ломает. Отдельно проверено, что обе проверки разметки ловят свою ошибку: фрагмент, записанный не за тем тендером, и фрагмент, развалившийся по границе чанков.

Эмбеддер GigaChat проверяется без сети и без ключа, причём подставляется клиент SDK, а не готовый эмбеддер: иначе тест проверял бы заглушку вместо разбора ответа. Проверено, что корпус уходит батчами, что векторы раскладываются по полю `index`, а не по порядку прибытия (перепутанные местами векторы ошибки не дают, чанки просто молча получают чужие эмбеддинги), что вектор чужой длины до индекса не доходит и что исчерпанный тариф не повторяется. Отдельно, уже в базе, проверено, что схема отказывается принимать эмбеддер другой размерности.

Повторы вокруг вызова LLM вынесены в отдельный тест: временный отказ повторяется, исчерпанный тариф не повторяется вовсе, чужая ошибка проходит наружу своим типом. `sleep` подставляется параметром, иначе тест на три попытки спал бы шесть секунд.

## Дальше

- замер на GigaEmbeddings: бэкенд готов, нужен пересбор индекса под 1024 и оплаченный пакет токенов
- размер набора: 46 вопросов дают шаг 0.02 по hit@5, и различать изменения мельче этого шага замер не умеет
- восемь вопросов не находит ни один режим на `e5-base`, и четыре из них находит `e5-small`. Это не про размер модели, а про то, что ни одна из двух не берёт вопрос, собранный целиком из общей тендерной лексики. Тут нужен другой сигнал, а не другая модель
- охват автофильтра упирается в то, что в тридцати восьми вопросах из сорока шести имя заказчика не названо вовсе. Другие оси сужения (категория услуги, регион, год) на архиве закупок помогут слабо: заказчик владеет одним-двумя документами, а категория четвертью архива. Поднимать охват стоит не новыми осями фильтра, а сценарием, где закупка уже выбрана
- разметки на большом корпусе нет. Кривая выше снята на настоящих вопросах, но чужие закупки в ней синтетические, и проверить на них нечего: вопросов к ним никто не писал. Пока архив не наберётся, это потолок точности замера
